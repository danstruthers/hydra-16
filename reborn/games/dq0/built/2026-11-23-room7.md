## 1. The stubs: 6 bytes -> 4 (the world's and the minds')

Every call into a swapped part goes through a stub in the main RAM (swap.inc's SWFN). A stub was `jsr sw_call`, the
part's number and the function's address: 6 bytes. With SWSTUBOV set in a task's bank.s, a stub is `jsr sw_call`
and its own number: 4 bytes. The part and the function are in three tables, a byte a stub each (the config's segments
SWSTP, SWSTL and SWSTH), kept in an overlay's bank. sw_call (stubs 0-255) or sw_call2 (256 and on, each table's
second page) maps that bank into the window, reads the 3 bytes and maps the old bank back, all before the part is
copied in or called. When the function runs, the window holds the bank it held before. This is swload's own pattern;
speed12 already keeps SWTAB in overlay 2's bank this way.

- **The world** (dq0w): 282 stubs, 564 bytes. The tables (846 bytes) are in the new overlay 33.
- **The minds** (dq0d): 64 stubs, 128 bytes. The tables (192 bytes) are in overlay 1 (1,650 -> 1,458 free).
- **Time:** about 25 cycles more a call. No part copy is added anywhere: the calls and the parts are the same.
- **The other tasks** (dq0, dq0p, dq0harn, dq0m) don't set SWSTUBOV and assemble the 6-byte stubs as before.
- **The guards:** dq0guards finds sw_call's `inc swsp` within 64 bytes of sw_call. It is 62 bytes in, because the
  second page's reads (swpage2) are out of line, after sw_back. dq0guards passes, and its swap guard is still hit.
- **The packer** (parts.js) can't see bank.s's segment sizes (bank.s is assembled after parts.inc is made). It now
  counts the three tables itself, a byte a stub each, from the stubs it has already found. step1's SWTAB count sits
  beside it.

  and its square was the old one; later its attitude went back as well. The world had the rat's body copied out
  (bd_get) for an intent already under way, so its bd_put wrote the old values back over the poke. No rat engaged,
  and each mid-round line waited out NO_ROUND_MID (400M) and was typed with no round.

  lines were never typed ("8 lines typed mid-round, not 12", "% echo $status" missing).

step1 saw the same mechanism (its open question 8: a version that held the body longer at each step lost the poke 3
runs of 3). **On room7's build dq0fightmid passes all three games, before step1 and after**, so I didn't re-set it.
If it fails again, the remedy is an -R offset on its menacing game, as dq0felled has.
