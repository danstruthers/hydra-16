# The character as actor 0: its record in the hub's table of bodies

As built, for review.  Branch actor0, 2026-11-17: ONE-PATH.md's stage 1, its first half ("the character as actor 0:
the hub's actor table, every task, the save"), by the user's choice of 2026-11-17 (DECISIONS.md's "The one-path plan
and phase A's questions: the user's answers": "The character becomes actor 0 first: its record moved into the hub's
actor table, then every act rebuilt on it").  The record and every task reading it; the acts are rebuilt on it by
later branches.

## The design (written before it was built)

### 1. The shape: one table of bodies, by who

Every message, request and event already names an actor by **who**: 0 the character, an actor's entry plus 1 (struct
msg's who, the world's `wk.who`, the referee's `r->actor`, the senses' eyes `E[1 + NACTORS]`).  The table takes that
numbering:

```c
union {
    struct actor    bodies[1 + NACTORS];        /* Every body, by who: 0 the character, k + 1 the denizens' entry k */
    struct {
        union {
            struct actor pc;                    /* Actor 0: the character's body (bodies[0]) */
            ...                                 /* (its fields by their old names: 3 below) */
        };
        struct actor actor[NACTORS];            /* The denizens' (actor[k] is bodies[k + 1]) */
    };
};
```

- **One record shape for every body.**  The character's body is a `struct actor`, the same as a denizen's, in the
  same table: `HUB->bodies[who]` is any actor's body, the character's included.
- **The denizens' entries keep their numbers.**  `HUB->actor[k]` is the same denizen's body as before, at k: the
  minds' records, the di ring's `who - 1`, the tests' pokes and the other branches' code keep their meaning.
  Numbering the denizens from 1 in one array would have changed every `actor[k]` and `who - 1` in every task, and a
  merged line from another branch would still compile with the old meaning: a silent fault.  The union costs nothing:
  the same bytes, two names.
- **Every loop over `actor[k]` (k from 0 to NACTORS - 1) is over the denizens**, and so skips actor 0 by
  construction: the minds never think for it (its mind is the UI, the player).  A loop for every body goes over
  `bodies[0 .. NACTORS]`, and says so by its name.
- Placed where `actor[NACTORS]` was in struct hub; the hub's version 56.

### 3. The old names kept

Each old name is laid over its field of actor 0 in hub.h, an anonymous member a line, placed by `offsetof`:

```c
struct { unsigned char _a0x[offsetof (struct actor, x)]; volatile unsigned pc_x; };
```

- `HUB->pc_x` reads and writes `HUB->pc.x`, the same bytes: no task's code changes, and the other branches' merges
  stay small.
- **Not macros** (`#define pc_x pc.x`): the UI has a variable of its own named `pc_face` (main.c's copy for the
  overlays), `gait` is a field's name in other structs (`struct actor`'s, the save's, the referee's), and a macro
  would rewrite any later local or field of its name in every file that includes hub.h.
- The old names keep their `volatile`; cc65 makes the same code with or without it (checked).
- hubgen.js lays out anonymous members (the union, the old names): obj/gen/dq0hub.json has every path, `pc_x`,
  `pc.x`, `bodies[0].x`, `actor[3].x`, so the tests and tools that read the hub by name read it as before.
- A task moves to the new names in its own time (`HUB->pc.x`, or `HUB->bodies[who].x` where the code is for any
  body); an old name goes once no task uses it.

### 4. Room

- **The hub's header (bank 0)**: `struct hub` grows by a ninth body less the seven fields moved, 53 - 12 = 41 bytes
  (some 5,882 to 5,923), leaving some 2,269 of bank 0's 8,192 free against the 2,048 HUB_FREE keeps.
- **Code**: the same in every task: `HUB->pc_x` and `HUB->pc.x` are one absolute address.  The world's `pc.state = 1`
  is a few bytes in part 16.  To be measured, each task, part and overlay.

### 5. The save

world.dat (`struct wsave`) keeps values, not the hub's layout: the world copies the character's fields into it by
name, and back.  Moving the fields in the hub leaves its bytes as they were, so **no conversion is needed, and old
saves load as they are**.  (game.dat, dens.dat, items.dat and the change records hold no hub layout either.)  Checked
byte for byte over several seeds: a game saved, carried on and saved again, the files the same; and the same files
written by bc75b074's build.

A conversion comes with the first stage that changes what world.dat keeps (the body's hiding in `state`, say, or the
body record kept whole): world.dat's version 5, version 4 converted on load, and dq0life and dq0end, which read
world.dat's clock, taking both.

### 6. The loops over actors

Every loop over `actor[k]` stays the denizens': none takes in actor 0 in this stage, since each would change what
happens now (the character would block its own way, see, engage, hear, name or count itself).  Each is listed below
with the stage that should take actor 0 in, by going over `bodies[]`.
