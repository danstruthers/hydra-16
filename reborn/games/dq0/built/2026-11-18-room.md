# Room won back: the headroom rule's list before the next features

As built, for review.  Branch room, 2026-11-18, from reborn-commands' bdf3a1ad.  The headroom rule (the user's): a
part or bank under 64 bytes free, or a task's main RAM within 64 of its floor, has its room won back before the next
feature.  The last build listed 42 items.  This branch clears 31 of them and leaves 11, each said below.  No game's
words change.

## What was built

1. **The packer keeps 64 bytes free in every bank** (games/dq0/parts.js).  Most of the world's 20 overlays on the list
   were full because the parts' packer filled each bank it chose to the byte.  It used best fit, and placed every part
   of the world again, biggest first, so its spare room piled up in a few banks.  The rule names banks, so it stays as
   it is; the packer changes instead:
   - banks() now takes a spare: each bank keeps that much free, if its own code leaves it.  A bank whose own code
     leaves less keeps what it has, and no part is put in it.
   - spread() asks for 64 everywhere.  If a task's parts can't fit so, it finds the one bank whose spare stops them
     fitting, gives that bank the most spare that still lets them fit, and keeps 64 in every other bank.  Failing that
     too, it gives every bank the same, as much as fits.
   - Each task's result is written to obj/games/TASK/spare.txt.
   - banksChecked's rules, with no spare kept, are as before.

   Per task:
   - **The UI, the world, the minds:** 64 in every bank; the total allows it.
   - **The referee:** 64 everywhere but overlay 4, which keeps 2 (below).
   - **The senses and the maker:** no bank was under 64.

   **The phrase table's banks** (saidgen.js, the UI's overlays 28-30) are filled in order. Each is now filled to 64
   short of full when all the rows fit so (22,797 bytes in 3 x 8,128), with a block that fits nowhere so taking the
   first bank with room to its end. Overlays 28 and 29 keep 65 and 67 bytes; 30 takes the rest.
2. **The theme tools' index read through Dt** (themegen/data.c, themec's and themegen's).  tg_load read the index into
a
255-byte buffer of its own. It now reads into the line buffer Dt, which no line uses yet at that point; a macro keeps
   the same absolute code.  This gives back 255 bytes of main RAM in each tool.
3. **The UI's and the minds' swap areas grow by 64 bytes** (dq0.cfg $1100 to $1140; dq0d.cfg $0F00 to $0F40).
   - A part's room is its swap area less its size, so every part of theirs gains 64. That clears the UI's parts 4 and
     9 and the minds' part 2.
   - The bytes come from their main RAM, which was 295 and 903 bytes over its floor.
   - No code moves. The area's top is where it was, and so is the C stack's floor.
4. **The referee's hub_attach in its part 4** (dq0/hub.c's HUB_ATTACH_P4, dq0harn/hub.c).
   - hub_attach and find_banks (185 bytes) run once, as the referee starts, after its overlays are read in.
   - They move into part 4, which had 4,456 bytes free. The world (HUB_ATTACH_SW3) and the senses (HUB_ATTACH_P3)
     already do the same.
   - The stub costs 6 bytes of main RAM; the net gain is 179.
5. **The ceiling's words said once in the UI's overlay 2** (words.c).
   - The glance and the close look each had their own " The ceiling is flat", " ... a dome,", " ... rough stone" and
     " The ceiling slopes".
   - Each is now one string, and the close look adds the rest after it: the same words, 58 bytes fewer.
6. **The referee's outfit code moves to overlay 6** (outfit.c, bank.s).
   - outfit.c (1,054 bytes) was in overlay 7, which had 47 bytes free. It goes to overlay 6, which had 2,497.
   - Its one call is through its stub, and its one call into overlay 7 (set_load) goes through that overlay's stub,
     like any call between overlays.

## Not cleared, and why

- **dq0harn overlay 4 (2 bytes free).**
  - It holds nothing but parts 1 and 3 (4,836 and 3,354 bytes). The packer must put them there, because no other bank
    has 3,418 bytes free; the most any has is 1,536.
  - Clearing it needs 62 bytes of real saving in those two parts (hmchar's file read and written; a dig's tool and
    the tests).
- **The world's parts 6, 23, 24, 25, 35, 58, 59, 81, 82 and 86** (between 1 and 55 bytes free).
  - A part's room is the world's swap area, 3,648 bytes. The world's main RAM is 2,115 bytes free, 67 over its floor,
    so the area can't grow the way the UI's and the minds' did without first winning about 61 bytes of main RAM.
  - The parts are code, with little read-only data and almost no duplicate strings.
  - Part 6 is one function, s_blows (3,593 bytes), so it can't be split. pack.js's piece mover, asked for 64 free in
    each of the ten (DQ0_PACK_SQUEEZE), stops there: "no piece of it can move".
  - For the rest, the mover would move functions into parts with room, but that is moving code, and each moved call
    would become a part swap, which costs time.
  - Real savings across the ten (some 416 bytes) are a job of their own, and an open question below.

## What the player sees differently

Nothing: no game's words change, and no logic changes.

- Bytes move between banks and between main RAM and the swap areas.
- Two functions start from a part (hub_attach) or another overlay (outfit_of).
- A buffer is shared, and four strings are said in two pieces.

## Open questions

1. **The world's ten short parts.** How should their room come back? Three ways, each needing a decision:
   - win about 61 bytes of the world's main RAM, and grow its swap area by 64. Candidates are BSS used only as one
     part's scratch (kind_of's four 37-byte kind buffers, if two will do; store.c's buffers are shared too widely);
   - let pack.js's mover move pieces into roomy parts, at a swap's cost per call;
   - or find real savings part by part (s_blows, part 6, needs 9).
2. **The referee's overlay 4.** Is 62 bytes of saving in hmchar's file code (part 1) or the dig tool's tests (part 3)
   worth it, or should a bank be freed for part 3 (3,418 bytes) by moving another overlay's code?
