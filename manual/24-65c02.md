# Chapter 24. The 65C02

The Hydra's processor is a **W65C02S**, made by the Western Design Center (WDC). It's the newest member of a famous
family. Its ancestor, the **6502**, was designed in 1975 by a small team at MOS Technology, among them Chuck Peddle
and Bill Mensch. It was cheap, simple and quick, and it became the heart of the home computer revolution: the Apple
II, the Commodore PET, VIC-20 and 64 (a 6510, a 6502 with a port added), the BBC Micro and the Atari 400 and 800 all
had one, and the Atari 2600 and the Nintendo Entertainment System used versions of it. Bill Mensch went on to start
WDC, which still makes the 65C02 today. The "C" means it's made in CMOS, which needs very little power; the "S"
means it's **static**: its clock can be slowed down, or even stopped, without losing anything.

This chapter explains how the 65C02 works, as you need to know it to write machine language for the Hydra. WDC's
data sheet for the W65C02S has every detail of the chip itself (section 24.13 says where to find it), and Appendix D
lists every instruction.

## 24.1 Machine code

The processor does one thing, over and over, millions of times a second:

1. It reads the byte at the address in its **program counter** (PC). That byte is an **opcode**: the number of an
   instruction.
2. If the instruction needs more, it reads the byte or two after it: its **operand**, such as a number or an
   address.
3. It does the instruction, and moves the program counter on to the next one (or, for a jump, to somewhere else).

A program in this form, as bytes, is **machine code**. The bytes `A9 41` mean "load the number $41 into the A
register": $A9 is the opcode of that instruction, and $41 is its operand. Nobody wants to write programs as numbers,
so each instruction has a short name, its **mnemonic**: $A9 is `LDA #`, "load A with this number". Programs written
with the names are **assembly language**, and a program that turns them into machine code is an **assembler**. The
Hydra's is called `as` (Chapter 25). `lda #$41` is assembled to `A9 41`.

Each 65C02 instruction is one, two or three bytes long: its opcode, then nothing, a byte, or an address. The 65C02
has 70 instructions (212 opcodes, counting each instruction's different ways of finding its data). They're all very
simple: each moves a byte, adds, compares, tests, or jumps. Big programs are made of many small steps.

## 24.2 Bytes, hex, and negative numbers

Chapter 17 explained bits, bytes and hexadecimal. The 65C02 works on **bytes**: eight bits, holding a number from 0
to 255 ($00 to $FF). An address is 16 bits, from $0000 to $FFFF, so it takes two bytes. The 65C02 always keeps the
two bytes of a 16-bit number **low byte first**: the address $F950 is stored as the bytes `50 F9`. (This is called
**little-endian**.) The assembler writes `<` for a number's low byte and `>` for its high byte: `<$F950` is $50, and
`>$F950` is $F9.

A byte can also hold a **negative number**. The trick is called **two's complement**: the bytes $80 to $FF stand for
-128 to -1. So $FF is -1, $FE is -2, and $80 is -128. Bit 7 is set in every negative number, which makes them easy to
spot. The nice thing about two's complement is that adding works the same either way: $FF + $01 is $00 (with a carry
out of the top), and -1 + 1 is 0.

| Byte | As a number from 0 to 255 | As a signed number |
|---|---|---|
| $00 | 0 | 0 |
| $01 | 1 | 1 |
| $7F | 127 | 127 |
| $80 | 128 | -128 |
| $FE | 254 | -2 |
| $FF | 255 | -1 |

The processor doesn't know which you mean: it's the program that decides how to read a byte.

## 24.3 The registers

Inside the 65C02 are six **registers**: tiny memories that the processor works with directly.

| Register | Size | What it's for |
|---|---|---|
| A | 8 bits | The **accumulator**: arithmetic and logic are done here |
| X | 8 bits | An **index register**: counting, and pointing into tables |
| Y | 8 bits | Another index register |
| S | 8 bits | The **stack pointer**: where the next byte pushed on the stack goes ($0100 + S) |
| PC | 16 bits | The **program counter**: the address of the next instruction |
| P | 8 bits | The **processor status**: eight flags, set by what the last instructions did |

The status register's bits are its **flags**:

| Bit | 7 | 6 | 5 | 4 | 3 | 2 | 1 | 0 |
|---|---|---|---|---|---|---|---|---|
| Flag | N | V | - | B | D | I | Z | C |

* **N**, negative: bit 7 of the last result (1 if it was negative, as a signed number).
* **V**, overflow: 1 if the last addition or subtraction went past the signed range (-128 to 127).
* **B**, break: only seen in a copy of P pushed on the stack: 1 if a `BRK` or `PHP` pushed it.
* **D**, decimal: 1 makes `ADC` and `SBC` work in decimal (section 24.8).
* **I**, interrupt disable: 1 holds interrupts off (section 24.11).
* **Z**, zero: 1 if the last result was zero.
* **C**, carry: the bit carried out of an addition (or 1 for no borrow in a subtraction), or the bit shifted out of a
  shift.
* Bit 5 isn't used.

Most instructions that change a register set N and Z by the new value. Appendix D shows which flags each instruction
changes.

## 24.4 Try it: watching the registers

The debugger, `db`, can run a program one instruction at a time and show the registers after each one. Chapter 27 is
all about it, but you can try it now. Here's a tiny program, `try.s`:

<!-- listing samples/try.s -->

```text
; try - a few instructions, to watch in db
.include "hydra.inc"
.include "hyx2.inc"

            HYX2_PROGRAM "try", main

.code
main:       lda #$7F            ; A = $7F (127)
            clc                 ; C = 0
            adc #1              ; A = A + 1 + C
            ldx #$FF            ; X = $FF
            inx                 ; X = X + 1
            rts                 ; The end
```

Go to `/ram` (`cd /ram`) and type it into the file `try.s` with the screen editor, `edit try.s` (Chapter 10 tells
you how to use it). Copy it exactly, but the comments, after the `;`s, can be left out. Then assemble it with `as`,
and start it in `db`. `s` steps one instruction:

<!-- session
cd /ram
!file samples/try.s
-->

```session
/ram> as try.s
/ram> db ./try
task 5
PC=0830 A=30 X=FF Y=00 S=FD P=nv--dizc W=0 U=0 RAM=00 ROM=00
0830  A9 7F     lda #$7F
db> s
PC=0832 A=7F X=FF Y=00 S=FD P=nv--dizc W=0 U=0 RAM=00 ROM=00
0832  18        clc
db> s
PC=0833 A=7F X=FF Y=00 S=FD P=nv--dizc W=0 U=0 RAM=00 ROM=00
0833  69 01     adc #$01
db> s
PC=0835 A=80 X=FF Y=00 S=FD P=NV--dizc W=0 U=0 RAM=00 ROM=00
0835  A2 FF     ldx #$FF
db> s
PC=0837 A=80 X=FF Y=00 S=FD P=NV--dizc W=0 U=0 RAM=00 ROM=00
0837  E8        inx
db> s
PC=0838 A=80 X=00 Y=00 S=FD P=nV--diZc W=0 U=0 RAM=00 ROM=00
0838  60        rts
db> q
```

Each line starting `PC=` shows the registers, and the line under it the next instruction: its address, its bytes,
and the instruction. In `P`, a capital letter is a flag that's 1, and a small one a flag that's 0. Follow it through:

* `lda #$7F` put $7F in A. (The registers started with what was left in them: they're not cleared.)
* `adc #1` added 1 (and the carry, 0): $7F + 1 = $80. The result has bit 7 set, so **N** became 1. And 127 + 1 is
  128, too big for a signed byte, which wrapped round to -128: so **V**, overflow, became 1 too.
* `ldx #$FF` put $FF in X. N stayed 1, because $FF has bit 7 set.
* `inx` added 1 to X: $FF + 1 wraps round to $00. So **Z** became 1 (the result is zero), and N became 0.

`q` quits the debugger (and the program). The other numbers on the line are the Hydra's: `W` and `U` are two of its
registers (section 6.2), and `RAM` and `ROM` the task's bank registers.

## 24.5 Memory

The 65C02 sees 65,536 bytes: addresses $0000 to $FFFF. Memory is thought of in **pages** of 256 bytes: page $00 is
$0000-$00FF, page $01 is $0100-$01FF, and so on. The high byte of an address is its page.

Two pages are special:

* **Page 0**, the **zero page** ($0000-$00FF). Its addresses need only one byte, so instructions that use them are
  shorter and quicker. The zero page is also the only place a pointer can be kept (section 24.6). Programs use the
  zero page for their most important variables.
* **Page 1**, the **stack** ($0100-$01FF). The 65C02 keeps its stack here (section 24.10).

On the Hydra each task has its own 32K at $0000-$7FFF (section 6.3), so every program has a zero page and a stack
of its own. A program in assembly language sees its memory like this:

| Addresses | What's there | For the program? |
|---|---|---|
| $00, $01 | The task's RAM and ROM bank registers | Read them; write them to choose a bank |
| $02-$21 | r0 to r15, the **call registers**: values going to and from HydraOS | Yes, but every system call can change them |
| $22-$7F | The program's zero page: 94 bytes | Yes: all its own. HydraOS never touches them |
| $80-$FF | HydraOS's zero page for this task | No |
| $0100-$01FF | The stack | Through the stack instructions |
| $0200-$03FF | HydraOS's area for this task (its open files, its name ...) | No |
| $0800-$7FFF | The program: its code, its data, and its BSS (its variables, cleared as it starts) | Yes |
| $8000-$9FFF | The RAM bank chosen by $00 | Yes (section 25.15) |
| $A000-$DFFF | The paged ROM bank chosen by $01 (the libraries, and the ROM disk) | Read only |
| $E000-$FFFF | The kernel, the I/O ports and the Hydra's registers | No: through system calls |

A program file is loaded at $0800. Its first 48 bytes are its **header** (who it is, how long it is, where it
starts), so the first instruction is usually at $0830. After the program comes its BSS, then free memory up to the
**break**, which a program can move with the `BREAK` system call to get more.

## 24.6 Addressing modes

An instruction that works on memory has to say which byte. The ways it can say are its **addressing modes**. Here
they all are, as the assembler writes them. *M* means the byte the instruction works on.

| Mode | Written | Bytes | *M* is |
|---|---|---|---|
| Implied | `inx` | 1 | (No memory: the instruction says it all) |
| Accumulator | `asl a` | 1 | The A register itself |
| Immediate | `lda #$41` | 2 | The number written: $41 |
| Zero page | `lda $22` | 2 | The byte at $0022 |
| Zero page, X | `lda $22,x` | 2 | The byte at $22 + X (staying on the zero page) |
| Zero page, Y | `ldx $22,y` | 2 | The byte at $22 + Y (`LDX` and `STX` only) |
| Absolute | `lda $1234` | 3 | The byte at $1234 |
| Absolute, X | `lda $1234,x` | 3 | The byte at $1234 + X |
| Absolute, Y | `lda $1234,y` | 3 | The byte at $1234 + Y |
| Zero page indirect | `lda ($22)` | 2 | The byte at the address kept in $22 and $23 |
| Indirect, Y | `lda ($22),y` | 2 | The byte at (the address kept in $22 and $23) + Y |
| Indexed indirect | `lda ($22,x)` | 2 | The byte at the address kept in $22 + X and the byte after |
| Absolute indirect | `jmp ($1234)` | 3 | (`JMP` only) Jump to the address kept at $1234 and $1235 |
| Absolute indexed indirect | `jmp ($1234,x)` | 3 | (`JMP` only) Jump to the address kept at $1234 + X |
| Relative | `bne loop` | 2 | (Branches) Go to `loop`: up to 128 bytes back, or 127 forward |
| Zero page, relative | `bbr0 $22,loop` | 3 | (`BBR`, `BBS`) Test a bit of $22, and maybe go to `loop` |

The `#` is important: `lda #$41` loads the number $41, but `lda $41` loads the byte at address $0041. Forgetting
the `#` is the commonest mistake in assembly language.

**Indexing** adds X or Y to an address, which is how a program steps through a table or a string. This loop prints
the string at `text`, a byte at a time, until it reaches the 0 at its end:

```text
            ldy #0              ; Y = 0: the first character
loop:       lda text,y          ; A = the character at text + Y
            beq done            ; (0: the end)
            jsr PUTC            ; Print it
            iny                 ; The next one
            bne loop
done:
```

**Indirect** modes use a **pointer**: an address kept in two bytes of the zero page. `lda ($22),y` reads the address
kept at $22 and $23, adds Y, and loads the byte there. Since the pointer can be changed, one piece of code can work on
any string or table. The Hydra's system calls pass pointers this way, in r0 to r15.

## 24.7 Moving bytes

| Instructions | What they do |
|---|---|
| `LDA`, `LDX`, `LDY` | **Load** A, X or Y from memory (or with a number) |
| `STA`, `STX`, `STY` | **Store** A, X or Y into memory |
| `STZ` | Store zero into memory |
| `TAX`, `TAY`, `TXA`, `TYA` | **Transfer**: copy A to X, A to Y, X to A, Y to A |
| `TSX`, `TXS` | Copy S to X, X to S |

Loads and transfers (except `TXS`) set N and Z by the value. Stores don't change any flags. There's no instruction to
copy one byte of memory straight to another: a program loads it into a register, then stores it.

```text
            lda #5              ; A = 5
            sta count           ; count = A
            ldx count           ; X = count
            stz total           ; total = 0
```

## 24.8 Arithmetic

The 65C02 can add and subtract, and nothing more: multiplying and dividing are done by programs (or, on the Hydra,
the numbers library, section 25.16).

| Instructions | What they do |
|---|---|
| `ADC` | A = A + *M* + C (**add with carry**) |
| `SBC` | A = A - *M* - (1 - C) (**subtract with borrow**) |
| `INC`, `DEC` | Add 1 to, or take 1 from, a byte of memory (or A) |
| `INX`, `INY`, `DEX`, `DEY` | Add 1 to, or take 1 from, X or Y |
| `CLC`, `SEC` | Make C 0, or 1 |

There's no plain add: `ADC` always adds the carry too. So before adding, a program clears it with `CLC`; and before
subtracting, it sets it with `SEC` (C = 1 means "no borrow"). Why? Because the carry is how bigger numbers are added,
a byte at a time. This adds 1000 to the 16-bit number in `score` and `score + 1` (low byte first):

```text
            clc                 ; No carry into the low bytes
            lda score
            adc #<1000          ; The low bytes ($E8) ...
            sta score
            lda score + 1
            adc #>1000          ;   then the high bytes ($03), and the carry from the low
            sta score + 1
```

If the low bytes' sum is more than 255, C becomes 1 and the second `ADC` adds it in, exactly as you carry a 1 when
you add on paper. `INC`, `DEC` and the others don't change C; they set N and Z.

**Decimal mode.** After `SED` (set D), `ADC` and `SBC` work in **binary-coded decimal**: each half of a byte holds a
digit from 0 to 9, so $19 + $01 gives $20, not $1A. Scores on old arcade games were often kept this way, because
they're easy to print. `CLD` goes back to binary. Always `CLD` when you're done: HydraOS expects D to be 0.

## 24.9 Logic, bits and shifts

| Instructions | What they do |
|---|---|
| `AND` | A = A AND *M*: a bit is 1 only where both are 1 (to clear bits) |
| `ORA` | A = A OR *M*: a bit is 1 where either is 1 (to set bits) |
| `EOR` | A = A XOR *M*: a bit is 1 where they're different (to flip bits) |
| `BIT` | Test: Z = 1 if A AND *M* is 0; N and V get bits 7 and 6 of *M* |
| `TSB`, `TRB` | **Test and set** or **test and reset**: set or clear in *M* the bits that are 1 in A |
| `RMB`*n*, `SMB`*n* | Clear or set bit *n* (0 to 7) of a byte on the zero page |
| `ASL`, `LSR` | Shift left or right one bit: the bit shifted out goes into C, a 0 comes in |
| `ROL`, `ROR` | Rotate left or right through C: the bit shifted out goes into C, and C comes in |

`AND #$DF` clears bit 5, which turns a small letter into a capital (the `upper` sample on the SD card does just
that). Shifting left multiplies by 2, and shifting right divides by 2:

```text
            lda #6
            asl a               ; A = 12
            asl a               ; A = 24
            lsr a               ; A = 12
```

## 24.10 Comparing, branching and the stack

**Comparing.** `CMP`, `CPX` and `CPY` compare A, X or Y with *M*. They subtract, but keep only the flags:

| After `CMP` | Z | C | Branch with |
|---|---|---|---|
| A equals *M* | 1 | 1 | `BEQ` |
| A is not *M* | 0 | | `BNE` |
| A is less than *M* (from 0 to 255) | 0 | 0 | `BCC` |
| A is *M* or more | | 1 | `BCS` |

**Branching.** A branch goes somewhere else if a flag is set (or clear), and on to the next instruction if not:

| Instruction | Goes if |
|---|---|
| `BEQ`, `BNE` | Z = 1 (equal, or zero); Z = 0 |
| `BCS`, `BCC` | C = 1; C = 0 |
| `BMI`, `BPL` | N = 1 (minus); N = 0 (plus) |
| `BVS`, `BVC` | V = 1; V = 0 |
| `BRA` | Always |
| `BBR`*n*, `BBS`*n* | Bit *n* of a zero page byte is 0; is 1 |

A branch can reach 128 bytes back or 127 bytes forward. For further, `JMP` goes anywhere. This loop counts X down
from 10, doing its work 10 times:

```text
            ldx #10             ; 10 times
again:      ...                 ; (The work)
            dex                 ; X = X - 1, and Z = 1 when it's 0
            bne again           ; Again, until X is 0
```

**Subroutines.** `JSR` (jump to subroutine) jumps to a piece of code and remembers where it came from; `RTS` (return
from subroutine) goes back there. The return address is kept on the **stack**: a pile of bytes in page 1. Pushing a
byte puts it at $0100 + S, then takes 1 from S; pulling adds 1 to S, then reads it. So the stack grows downwards,
and the last byte pushed is the first pulled. `JSR` pushes two bytes (the address of its own last byte: `RTS` adds 1),
and `RTS` pulls them.

| Instructions | What they do |
|---|---|
| `JSR`, `RTS` | Call a subroutine; return from one |
| `JMP` | Jump |
| `PHA`, `PHX`, `PHY`, `PHP` | Push A, X, Y or P |
| `PLA`, `PLX`, `PLY`, `PLP` | Pull A, X, Y or P |

Pushing is the way to keep a register safe while something else uses it. A system call may change A, X and Y, so a
loop that counts with X keeps it on the stack over the call:

```text
            ldx #3              ; 3 times
loop:       phx                 ; Keep X ...
            lda #'*'
            jsr PUTC            ;   (PUTC may change it)
            plx                 ;   and have it back
            dex
            bne loop
```

Every push needs a pull. A subroutine that returns with more (or fewer) bytes on the stack than it found will
return to the wrong place. The stack has room for 256 bytes; a program starts with S = $FD.

## 24.11 Interrupts

An **interrupt** is a signal from a chip that something has happened: a key has come in, a timer has run out. The
65C02 finishes its instruction, pushes PC and P on the stack, sets I, and jumps to an **interrupt handler**; the
handler deals with the chip, and `RTI` (return from interrupt) pulls P and PC, so the program carries on as if
nothing had happened.

| Instructions | What they do |
|---|---|
| `SEI`, `CLI` | Set I (hold interrupts off), clear I (let them in) |
| `BRK` | A **software interrupt**: like an interrupt, but from an instruction |
| `RTI` | Return from an interrupt |
| `WAI` | Wait (asleep) for an interrupt |
| `STP` | Stop the processor until the next reset |

The 6502 has one interrupt line, so its handler has to ask every chip "was it you?". The Hydra does better: its
fifteen interrupt lines go to a **priority encoder** (U17 and U18), and its **vector RAM** gives each line its own
handler's address, so the 65C02 goes straight to the right one. Line 0 (the VIA, which makes the tick) comes first,
then the serial port, the Vera X, the YM2151 and the slots.

On the Hydra, the interrupts are HydraOS's. They're how it shares the processor between the tasks (the tick, two
hundred times a second), and how its drivers hear from their chips. So a program:

* leaves the I flag alone. (To keep the processor to itself for a moment, it uses the `PREEMPT_OFF` and `PREEMPT_ON`
  system calls.)
* never writes the Hydra's registers T, U, V and W, the vector RAM, or HydraOS's memory.
* never uses `STP`, which stops the whole Hydra, every task, until you press RESET.

A `BRK` in a program doesn't crash the Hydra: HydraOS sends the program a **note**, `sys: brk` (section 25.16 has
more on notes), which ends it unless it has a note handler. The debugger uses `BRK` for its
breakpoints (Chapter 27).

## 24.12 How fast?

The 65C02 does its work in **cycles**, ticks of its clock. On the Hydra, the clock is 3.58 MHz: 3,579,545 cycles a
second (the jumper J7, section 4.6). Each instruction takes from 2 to 7 cycles. `LDA #` takes 2, about half a
millionth of a second; `JSR` takes 6. Appendix D gives every instruction's cycles. So the Hydra does very roughly a
million instructions a second, shared between its tasks. Between two ticks of HydraOS's clock (200 a second) there
are about 17,900 cycles.

Machine code is the fastest a program can be. HydraOS's twenty benchmark programs (on the SD card, in `/sd/0/bench`)
run about 60 times faster written in assembly language, in HyBASIC's `ASM` blocks, than in HyBASIC itself.

## 24.13 Learning more

These are good places to go on from here:

* **WDC's W65C02S data sheet** (from wdc65xx.com): every instruction, its cycles and its flags, and the chip's pins
  and timing.
* *Programming the 65816* by David Eyes and Ron Lichty: the 65C02's instructions explained in depth, with the 6502's
  and the 65816's.
* *6502 Assembly Language Programming* by Lance Leventhal, and *Programming the 6502* by Rodnay Zaks: two classics
  from the 1980s, written for the 6502 (the 65C02 adds to it, and has fixed its few bugs).
* *Machine Language for the Commodore 64* by Jim Butterfield: a gentle start, for Commodore owners, but the 6502
  is the same.

The 65C02 has a few instructions the first 6502 didn't: `BRA`, `PHX`, `PHY`, `PLX`, `PLY`, `STZ`, `TRB`, `TSB`,
`WAI`, `STP`, the bit instructions `RMB`, `SMB`, `BBR` and `BBS`, the zero page indirect mode (`lda ($22)`), `INC A`
and `DEC A`, more modes for `BIT`, and `JMP ($1234,x)`. So a book about the 6502 teaches you everything but these.
